# DotMap

A world map drawn as dots, with the ones that matter in the accent.

```tsx
import { WORLD_DOTS } from './worldDots'

;<DotMap
  dots={[...WORLD_DOTS, [292.5, 243.5, 1, 'fra1 · 1.2m']]}
  label="Request origins, last hour"
/>
```

| prop             | default | notes                                                    |
| ---------------- | ------- | -------------------------------------------------------- |
| `dots`           | —       | `[x, y]`, `[x, y, 1]` for the accent, `[x, y, 1, label]` |
| `width`/`height` | 528/380 | user units **and** rendered px                           |
| `fit`            | `true`  | scale and centre the points into the box                 |
| `label`          | —       | required; the drawing's only text                        |

## The drawing is `drawMap`, and there is almost nothing to it

Every point is a `2.6×2.6` **rect** centred on its coordinate, filled either near-white or with a dimmer teal.
The replica fades them in left to right; that is deliberately not copied, because a staggered fade is a
page-level flourish rather than a property of the map.

**Two colours, both derived rather than copied.** The replica writes `#5be4dc` for an accented dot and
`rgba(255,255,255,.85)` for the rest. The first is the accent about 12% toward ink — a small dot at full
accent is a glare, so it is dimmed by the rule every other state here uses. The second is `--foreground` at
85%: white on the dark theme, near-black on the light one, which is the right behaviour for a map on a white
page that the replica never had to consider.

## The fit, and why the data forced it

The dataset's own range is about `x 81–482`, `y 144–401` — 401 tall — while the zone `dashboard.html` gives it
is `528×380`. The comment there says the dots are _"scaled ~0.93 into a 528×380 zone, centered"_, and that
scaling lives in the page, not in `drawMap`. Doing it here means the data and the box can change
independently, which is what makes this a component rather than a snippet. `Unfitted` asserts that the raw
coordinates really do put dots past the bottom edge, so the default is doing work rather than being decorative.

## The readout is opt-in through the data

**The replica's map has no tooltip, and cannot have one.** `GEO_DOTS` is bare geometry with no values, so
there is nothing to say about an individual point — a dot map here answers _where_, not _how much_.

Give a dot a fourth element and it becomes hoverable: the map finds the nearest labelled dot within **10
units** of the pointer and shows its text above it. Unlabelled dots are skipped, so a pointer over the ocean
finds nothing rather than the nearest coastline fragment.

It is `aria-hidden`, the same as the chart's readout: something that exists only under a pointer is not
available to a keyboard, so announcing it would claim an affordance this cannot keep. Where the values matter,
they belong in a `Table` beside the map.

## `WORLD_DOTS` is generated, not hand-written

`src/components/DotMap/worldDots.ts` holds 848 points, 69 of them accented, produced from
`pulse-replica/js/data.js`. It is data rather than design, so it lives in its own module: a consumer that
never draws the map never pays for it.

**Regenerate it with `node scripts/gen-world-dots.mjs`, not by editing the file.** The first version of
this was generated by a throwaway script that was then deleted, which left a derived file with no
derivation — indistinguishable from a hand-written one, and this doc telling a reader to regenerate it when
`data.js` changed, which was not possible. The script reads `GEO_DOTS` out of the replica's plain browser
script with a regex (it is a top-level `const`, not a module), parses the array as the JSON it already is,
and writes the module. Running it twice produces byte-identical output.

## It draws on a `<canvas>`, not an `<svg>`

The replica builds its map by appending ~850 `<rect>` elements into an `<svg>`. This draws the same `2.6`
squares with `fillRect` instead, because 850 DOM nodes for one picture is the cost a canvas exists to avoid —
and it makes the pointer handling cheaper, since hit-testing is already arithmetic against the dot list
rather than a listener per element.

**Canvas costs three things the SVG had for free, and each is handled rather than ignored:**

1. **A canvas cannot read `var()` or `color-mix()`.** `fillStyle` needs a concrete colour. The two fills are
   resolved by assigning the expression to the canvas's own `color` and reading back what the browser
   computed — the canvas has no text, so this paints nothing. That is what keeps `light-dark()` and the
   token derivations working, and the story asserts the two fills really differ, because a failure here
   would paint one fallback everywhere and still look like a map.
2. **A canvas must be redrawn when the theme changes.** The tokens are CSS, so flipping `data-theme` changes
   what they resolve to without touching React. A `MutationObserver` on the document element redraws;
   without it the map keeps whichever theme was active when it mounted.
3. **The readout cannot be a `<foreignObject>`.** It is an HTML panel in a wrapper around the canvas,
   positioned by percentage exactly as `BarChart`'s is.

**The device pixel ratio is applied.** The `width`/`height` attributes are the _bitmap_ size while the CSS
box is what is shown, so a retina display gets a blurred map unless the bitmap is scaled up and the context
scaled back down. The story asserts `canvas.width === 528 × dpr`.

## The assertions changed shape, and one of them got better

While this was an SVG, the stories read every `<rect>` back out of the DOM and checked where it landed. A
canvas has no such elements, so:

- **the geometry moved into `fitDots`, which is exported and asserted directly** — it is the part of this
  component that is a pure function, and testing it that way is better than reading it out of the DOM;
- **the drawing is now checked in pixels**, which the SVG version could not do at all. It samples the pixel
  at each fitted dot's own centre and classifies it by which of the two fills it is nearer — 60+ of the 69
  accented dots and 750+ of the rest.

The first version of that check counted _distinct_ colours, which is nearly meaningless here: the dots sit
on fractional coordinates, so every edge is antialiased and the bitmap holds hundreds of near-unique shades.
It passed, and would have passed for a map painted in a single colour. Counting exact shades failed the
other way — 33 of 69, 407 of 800 — because a 2.6px square at a fractional position straddles the sampled
pixel. Distance to a reference is the version that holds.
